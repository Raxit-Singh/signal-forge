# Architecture

## Shape

One Next.js application (UI, server actions, route handlers, and later the job worker endpoint) and one Supabase Postgres database. Postgres is also the queue, the lock service and the analytics store. This keeps the free-tier footprint to two services and the operational surface to one codebase.

```
Browser ──► Next.js (Vercel / any Node host)
              ├─ proxy.ts            refresh Supabase session, gate app routes
              ├─ Server Components   read via user-scoped client  ──► RLS
              ├─ Server Actions      validate (zod) → authorize → write via user client ──► RLS
              │                      (service role only for secrets / account deletion)
              ├─ /api/jobs/tick ◄── Supabase Cron (pg_cron + pg_net), shared secret
              │     └─ schedule due queries → claim jobs → adapters → relevance → ingest
              └─ after() on "Start scan" / "Start historical search" — works the first batch now
Supabase Postgres ──► Supabase Realtime (workspace_events, RLS per subscriber) ──► browser: refetch (router.refresh)
  ├─ auth.*            Supabase Auth (email+password, Google OAuth, email verification)
  ├─ public.*          tenant data, all RLS-protected, least-privilege grants
  └─ private.*         helper functions (not exposed by the Data API)
```

## Module boundaries (src/lib)

| Module | Rule |
|---|---|
| `domain/` | Pure TypeScript. No Next/Supabase imports. Unit-tested with `node --test`. Imports use explicit `.ts` extensions so Node can run them directly. |
| `validation/` | Zod schemas built on domain parsers. Every server action re-validates. |
| `server/` | `import "server-only"`. Session + authorization (`requireWorkspaceRole`), credential encryption, env. |
| `supabase/admin.ts` | Service-role client. Only after an explicit authorization check, always scoped by workspace id. |
| `sources/` | Pure TypeScript, no Next/Supabase imports: one adapter per public source, relevance rules, text normalization, ingest preparation. HTTP goes through an injected `SourceContext`, so every adapter is tested with deterministic fixtures. |
| `sources/apidirect/` | Pure: API Direct client (validation, `X-API-Key`, retries, error mapping, documented billing rules), endpoint catalog, zod response schemas, normalizers, the 10 paid connectors. |
| `sources/query-optimizer.ts`, `adaptive.ts`, `expansion.ts` | Pure, deterministic engines: per-platform query grouping + fingerprints, refresh-interval decisions, comment-expansion selection. |
| `sources/arrival.ts`, `adaptive-v2.ts`, `collection-profile.ts`, `resume.ts`, `backfill-plan.ts` | Pure (Discovery Engine V2): Gamma–Poisson arrival-rate model and page right-sizing; product-adaptive intervals, brand-safe pacing and overflow risk; per-stream provider vs application limits and history depth; resumable gaps (date-range splitting, page offsets); historical backfill planning. |
| `analytics/` | Pure buzz math: series with coverage gaps, growth, virality, spike detection (`spikes-v2.ts`: confirmed / possible / insufficient data), time zones. |
| `server/collection/` | Server-only glue: rate-limited + budget-reserving HTTP context, `monitor.query` job (shared fetches, expansion, adaptive scheduling, audits), worker loop, scheduler tick, query sync, coverage/scan status, Smart Monitoring overview. |
| `server/analytics/` | Buzz dashboard queries (RLS) and the hourly spike-detection job (service role; product, platform and keyword level). |
| `server/collection/backfill*.ts` | Historical search: start (plan-bounded range → one task per query group), the `backfill.task` job (bounded, resumable step), progress for the UI (RLS). |
| `components/realtime/` | Client: one workspace-scoped Realtime subscription per session (`RealtimeProvider`), debounced refetch, reconnect/visibility recovery, slow fallback polling, holds for pages that mustn't jump (older Mentions pages). |
| `ai/` (M4) | Provider abstraction: `classify`, `summarize`, `embed?`, token accounting, budget checks. |

### Source adapter interface

`src/lib/sources/types.ts`:

```ts
interface SourceAdapter {                       // public, keyword-searchable sources (17 platforms)
  id: PublicSourceId;
  dataProvider?: "official" | "apidirect"; paid?: boolean; shareable?: boolean;
  streams?: StreamSpec[];                       // separate checkpoints, e.g. Reddit posts / comments;
                                                // each declares QueryCapabilities (OR syntax, length,
                                                // terms, date filter, sort, pagination, page cap)
  expandComments?(parents, ctx): Promise<SearchResult>;   // platforms without global comment search
  configured(): { ok: true } | { ok: false; reason };     // server has the keys it needs
  rateLimit(endpoint?): RateLimitPolicy;        // shared Postgres token bucket(s)
  retentionDays?: number;                       // platform storage limits (YouTube: 30)
  searchMentions(req, ctx): Promise<{ items: CandidateMention[]; complete; incompleteReason?; rateLimit? }>;
  validateCredentials(ctx): Promise<void>;
}
interface AuthorizedSourceAdapter {             // reserved for App Store Connect, Play, Discord, GitHub App (M5–M6)
  connect(); disconnect(); validateCredentials(); fetchMention(); getIntegrationHealth();
}
```
Normalization is pure and exported per adapter. Rate-limit status is reported with each search result and stored in `source_health`. Paid requests go through `SourceContext.paidRequest`, which reserves budget **before** the HTTP call and must be settled with the provider's billing outcome afterwards; the API Direct client does this for every call, including retries.

### Multi-platform monitoring (Milestone 2.5)

```
keywords ──► query optimizer (per platform stream, capabilities-aware) ──► query groups + fingerprints
                                                                              │ apply_query_groups
scheduler (adaptive interval, plan floor) ──► monitor.query job ──► shared fetch (same fingerprint ⇒ one
                                                                     upstream call for every product)
   budget reservation (global → provider → platform → workspace/product/boost, advisory-locked)
   → API Direct / official API → normalize → per-product relevance → ingest (per paid request)
   → selective comment expansion → coverage window → adaptive decision → execution log
```

- **Query optimizer** (`planQueries`): OR-combines brand aliases where the platform supports OR, within length/term limits; phrases that contain a searched brand alias as a separate word are "covered"; ambiguous keywords are only searched with their context terms (platforms with grouping); category phrases get their own group; keywords differing only in case/spacing/quotes are one search (reported as duplicates); platforms without OR get one query per keyword — free ones search every keyword, paid ones up to the plan's `max_searches_per_platform` (default 2), highest-priority keywords first. Every keyword still drives local relevance matching, and every keyword not searched on a platform is shown with the reason (covered, duplicate, unsupported, ambiguous without context, plan cap, too long). `keyword-plan.ts` is the single planner used by the worker's query sync (`query-groups.ts`), the Smart Monitoring page, `npm run audit:keywords` and `scripts/resync-queries.ts` — for **all** sources, including Hacker News, Stack Overflow, GitHub and YouTube (their SQL first-5 sync is retired). **Keyword rotation:** where a platform has a search budget per check (paid without OR: plan's `max_searches_per_platform`; Stack Overflow without a key: 3) and needs more searches, the top search runs every check and the rest take turns in fixed time slots of one platform interval (`slot mod turns = position mod turns`, so no slot exceeds the budget and every search gets an equal share); `params.rotation` is stored on the group, its `interval_minutes` = platform interval × turns (the budget per check is never exceeded).
- **Plan entitlements** (`sources/entitlements.ts`, pure): *keyword allowance* — active keywords per workspace (Free 1, Pro 10, Scale 40) shared across active products in creation order; beyond it (after a downgrade) keywords are paused, not searched, shown as such (`applyKeywordAllowance`); a DB trigger (`product_aliases_enforce_limit`) refuses saves that exceed it. *Keyword refresh target* (`plans.keyword_refresh_target_minutes`: 7 d / 24 h / 6 h) shortens a platform's interval so its slowest keyword meets it, never below plan or source floors; unmet targets are stored in `platform_activity.keyword_conflict` with the real interval. *Paid pacing* (`paceForBudget`): projected spend to month end at those intervals vs the product's share of the workspace's remaining paid budget (`svc_paid_budget_context`); paid platforms are lengthened one step at a time, costliest first, until it fits (`budget_paced`).
- **Shared query registry:** `monitoring_queries.fingerprint` = sha256(platform, stream, normalized expression, language, region, filters). One job fetches once (under a named lock) and ingests for every product with the same fingerprint, each with its own relevance rules; cost is split across their budgets. Results are not cached afterwards. Product-specific sources (Trustpilot, App Store) include the product in the fingerprint, so they never share.
- **Checkpoints (V2, resumable):** `cursor.until` per query group (so per stream) plus `cursor.gap` — the part of an overflowing window not yet read (`[start, oldest result read]` for date-range sources, next page offset for page sources; `collection-profile.ts` says which). A regular run advances `until` to its window end; the gap is read by continuation jobs (`mq-cont:<query>:…`, 30 s later, own idempotency key) until done; a gap that stops progressing twice is closed and its window recorded as partial; sources that can't resume record the unreachable part as partial ("lost") at once. Checkpoints hold when the mention allowance held items back. Coverage records the read part as complete and lost parts as partial; a partial window wins over a complete one in analytics (migration 08). Page-billed calls request right-sized pages (`pagesToRequest`) with at most one escalation per run.
- **Product-adaptive engine V2** (`arrival.ts`, `adaptive-v2.ts`, `server/collection/activity.ts`; replaced the score → interval table on 2026-10-16). Per product × platform × query group:
  - *Arrival rates:* after every run, two Gamma–Poisson posteriors are updated (results/hour and relevant/hour) from the count and the window's exposure, with exponential forgetting (half-life 7 days); a saturated run counts only the time its results covered (newest-first) or half the window. Stored in `arrival_estimates`. The planning rate is the posterior's 90th percentile, so little data means checking sooner. A product-wide hour-of-day profile (≥ 200 mentions in 28 days, shrunk toward flat) scales the rate for the next interval.
  - *Activity importance:* each platform's smoothed share of the product's relevant mentions over 28 days (Dirichlet(1)) — product-relative, so two products with the same mix rank the same at any size. It tilts check frequency only. The stored platform rank is by 28-day relevant mention count (ties by platform id); platforms never checked are unranked (since 2026-10-18; learning platforms that have been checked are ranked).
  - *Collection urgency:* freshness — about 3 new relevant mentions per check, tilted by importance (√(fair share / share), 0.5–2×); brand safety — the longest interval at which arriving results stay within 80 % of what one check (plus continuations for range sources) can read with a 2σ margin. Rotating searches at overflow risk get out-of-turn checks instead of slowing everyone.
  - *Coverage uncertainty:* learning until 3 checks and 48 h of searched time (bounded at 4 h free / 6 h paid); no rate or risk is claimed from the prior alone; incomplete coverage blocks slow-downs.
  - *Stability:* speed up at once on overflow risk or spikes (otherwise ≤ 2 steps), slow down one ladder step only after the lower rate has persisted for max(24 h, 2 intervals), with a ±25 % dead band. Quiet platforms are explored at their ceiling (12–24 h), never stopped.
  - *Then* plan floor / Launch Boost / source floors, the keyword refresh target, and **brand-safe budget pacing** (`paceForBudgetSafely`): costliest first with interval-dependent (right-sized) cost, but never past a platform's brand-safe bound; if the budget can't cover that, the risk is stored (`collection_risk`, `risk_detail`: none / watch / at_risk / unavoidable) and requests beyond the budget are refused at request time. `platform_activity` stores share, arrival/day, planning rate, safe interval, risk and uncertainty (`model = arrival_v2`); the measured activity signals below are kept as context.
- **Automatic Smart Monitoring — measured signals** (`adaptive.ts`; replaced the customer-chosen Eco/Balanced/Priority modes on 2026-10-16 — `products.monitoring_mode` is kept but no longer read; since V2 the score and its interval table no longer set intervals):
  - *Signals* (`private.platform_activity_stats`, stored data only, no API calls): relevant original mentions in 24 h / previous 24 h / 7 d / 28 d, distinct authors, engagement vs the platform's own 75th percentile, spikes in 72 h, share of the last 7 days (and of the 3 weeks before) covered by complete checks, completed checks, saturation, failures, audit misses.
  - *Activity score 0–100*: base score from volume (45), historical baseline (20), unique authors (15), engagement (10), spikes (10) — log-scaled with caps and rescaled over the signals that can be measured (unmeasurable ones, e.g. AI feedback signals before M4, are listed as "not measured", never guessed) — plus ± momentum for growth (15) and acceleration (10). Saturated platforms get a floor of 55 (their counts are lower bounds). Baselines from weeks with < 50 % complete coverage are not used.
  - *Ranking*: by score, then 7-day mentions. Platforms in their **discovery phase** (< 3 completed checks, or < 7 days monitored without a completely covered week) are unranked and start at 4 h (paid 6 h), never slowed down.
  - *Interval*: score → 1/2/3/4/6/12/24 h (85/70/55/40/25/10 thresholds); paid platforms with score < 40 one step slower; spike ⇒ ≤ 2 h; recent saturation and audit misses one step faster; per-platform maximum (12 h for HN/GitHub/Stack Overflow/Bluesky). **Hysteresis:** speed up at once (two steps per decision, all the way for spikes/saturation); slow down one step only after the lower activity has persisted for max(24 h, 2 intervals), only outside a 5-point dead band, never during discovery or with low coverage confidence. Then limits: Launch Boost (≤ 3 h, down to the plan's boost minimum) or the plan floor, then source floors (YouTube 24 h). `recommended_interval` (activity) and `interval_minutes` (actual) are stored separately.
  - *When*: after every successful run (the finishing group schedules itself) and hourly for every product with monitoring; boosts re-rank immediately. Shorter intervals pull `next_run_at` in; a group with no success for 2 intervals + 1 h is pulled to now (missed-run recovery). Every change of a platform's interval is logged with its reasons in `monitoring_interval_changes`.
  - *Explanations*: deterministic templates (`explain.ts`) over the stored metrics; a platform with incomplete coverage is never called quiet.
  - Failures retry sooner (30 min × 2ⁿ, checkpoint held); audits weekly (paid platforms with score < 25: fortnightly).
  - *Development entitlement* (`domain/dev-entitlement.ts`): on `next dev` only (NODE_ENV=development, not a Vercel deployment), workspaces listed in `DEV_MONITORING_WORKSPACES` may use a lower plan floor (`DEV_MONITORING_MIN_INTERVAL_MINUTES`, ≥ 1 h). It changes nothing else: budgets, paid allowances, rate limiters and source floors still apply, and the page shows a notice while it's active.
- **Comment expansion** (`selectExpansions`): relevant parent posts scored by relevance × log(comments) × recency; revisited only when the discussion grew; 1–4 parents per run by activity score (one page each); cost tracked under its own purpose.
- **Cost control:** `provider_pricing` is the only price list. `reserve_api_spend` checks the global budget (no row ⇒ no paid calls), provider, platform, then each member's workspace allowance (plan allowance, optionally lowered), product budget and boost cap; members who can't pay are dropped. `settle_api_spend` applies the documented billing rules (answered = billed, including zero results; `pages=N` bills N; unanswered requests stay counted at their estimate as `unknown`). `billing_reconciliations` records invoices against the ledger.

### Keyword-first rankings (2026-10-18)

What the Smart Monitoring page shows (`analytics/keyword-ranking.ts`, pure; `server/collection/keyword-rankings.ts`):
- **Counts, not scores.** Rank = descending relevant-mention count in the selected period (the global date range), ties by name then id. Growth (vs the period of the same length just before, stated only when that period was ≥ 50 % monitored and non-empty), engagement, momentum and AI never change a rank.
- **Per keyword × platform** from `keyword_platform_counts(product, from, to)` (SQL, `SECURITY INVOKER`): relevant originals with a known publication time, grouped by matched keyword (case-insensitive against current `product_aliases`) and platform. A mention that matched several keywords counts once for **each keyword**; platform and product totals come from `buzz_totals`, where every mention counts **once** — so keyword rows don't add up to the total, by design. Mentions matched only by context (no keyword term) count in totals but no keyword.
- **Coverage states** per platform: *not scanned* (no successful check and no coverage window — no rank, never shown as 0), *learning*, *partial coverage* (failing, partial, or confidence below high), *monitored*. While any platform isn't "monitored" the page says rankings are based on observed mentions.
- **Prioritization** stays in the arrival engine (above): each keyword × platform search has its own measured arrival rate, so busier searches get shorter intervals (and out-of-turn checks when rotating), quiet ones keep their ceiling (≤ 24 h). Rank itself doesn't set intervals.
- **First scan:** a search that has never succeeded runs at once, even when it would otherwise wait for its rotation slot, so every keyword × platform gets a baseline; historical search (one task per search group) covers every keyword too. Rate limits, budgets and allowances apply per run as usual.
- **Brand term:** the product name is always a keyword (`ensureBrandTerm`, enforced in the save action; locked in the editor). An ambiguous name without context words stays off until context is added.

### Collection pipeline

1. **Query sync** (server, after every keyword save, source change and daily): the keyword planner writes every source's query groups via `svc_apply_query_groups` (all keywords; OR groups of ≤5 for GitHub/YouTube; one per keyword for HN/Stack Exchange). `private.sync_monitoring_queries` only checks authorization now.
2. **Schedule** (`private.schedule_due_queries`): due queries → `monitor.query` jobs, ordered by plan `scheduling_priority` (Scale > Pro > Free) then due time; idempotency key `mq:<query>:<interval bucket>[:f<failures>]`; interval from Smart Monitoring (plan floor; YouTube ≥ daily). While a workspace's mention allowance is used up, paid queries are not scheduled (moved to the period end) and free ones run at most daily.
3. **Search window:** from the query cursor minus a 2 h overlap (search indexes lag), or the scan's lookback. Overlap is safe because ingestion is idempotent.
4. **Relevance (deterministic):** whole-word keyword match → ambiguous keywords need a context term → exclusion terms veto → thread/video context alone gives a low-confidence "needs review" match. Matched terms and a 0–1 score are stored. Nothing is matched by AI yet (M4).
5. **Ingest** (`private.ingest_mentions`, atomic per batch): upsert on (product, source, external_id); re-seen items refresh engagement but never overwrite a user's relevance decision; exact duplicates (content hash, ≥60 normalized chars) and reposts (same shared link) are stored but linked to the earliest original. **Mention allowance:** the batch first locks the workspace's current `mention_usage_periods` row (`lock_usage_period`, created on demand, plan synced), so concurrent workers serialize. A new item is *billable* if it is an original with rule status `relevant` (interim policy until M4); billable items are stored with `billed_period_start` and counted; once consumption reaches the allowance, billable items go to `mention_overflow` (≤1,000 per workspace per period, kept until 30 days after the period; beyond that only counted) instead of `mentions`. Duplicates, reposts, re-seen items, `pending` and `irrelevant` items are stored but never counted. A trigger on `mentions.relevance_status` refunds a billed mention marked not relevant (current period only) and bills one marked relevant while allowance remains. `release_held_mentions` (admin) delivers held items into the current period's remaining allowance.
6. **Record:** coverage window (complete / partial with reason / failed), `source_health`, `api_usage_events`, query cursor.
7. **Errors:** rate limits and quotas → `defer_job` (no attempt consumed); transient → exponential backoff; auth/bad request → no retry; a dead job writes a *failed* coverage window so the gap is visible.
8. **Signal:** one `workspace_events` row per finished job (`mentions` when anything was stored, else `monitoring`; counts only, coalesced within 2 s per workspace/product/kind) — browsers refetch.

### Historical search (backfill)

Chosen per product at onboarding (Since launch — launch date required —, 7 / 30 / 90 / 180 / 365 days, or a custom date; default 30 days; bounded by the plan's `history_days`: Free 30, Pro 365, Scale 730) and on Smart Monitoring. `startBackfill` creates a `backfill_runs` row and one `backfill_tasks` row per enabled query group, with each source's reachable start (`collection-profile.ts` history depth; unconfigured sources "unavailable", paid ones "paused" while paid sources are off). `svc_schedule_backfills` (each tick) enqueues due tasks as `backfill.task` jobs (`bf:<task>:<step>:<failures>`), pausing them until renewal while the workspace's mention allowance is used up. Each job reads one bounded step of its window (right-sized pages, one escalation), ingests through the same allowance-metered path, records coverage, and stores the remaining gap in `cursor`; it re-enqueues itself 20 s later while a gap remains. States: queued, searching, partially collected (a provider limit was hit), paused (allowance, paid budget, paid sources off), completed, unavailable — no percentages (totals aren't knowable). Backfills use publication time, so history fills past periods and never creates a "today" spike; they don't update arrival estimates (only regular checks and their continuations do).

### Realtime dashboard

`workspace_events` is in the `supabase_realtime` publication; postgres_changes applies each subscriber's RLS (`has_workspace_role(workspace_id, 'viewer')`), so a member only ever receives their own workspace's events, and events carry counts only (no mention text, credentials or prices). `RealtimeProvider` (in the app layout, keyed by workspace) subscribes with the user's token (re-set on token refresh, dropped on sign-out), ignores other products' events, and refreshes server components debounced (1.5 s, ≥ 4 s apart) — pages re-read authoritative data through RLS. Recovery: a catch-up refresh 2.5 s after first connect (events between render and subscription), one refresh after any reconnect, after a tab was hidden > 30 s and on `online`; while disconnected, a refresh every 60 s (visible tabs only). The Mentions page holds refreshes on older pages and shows "X new mentions found — View latest" (counted through RLS), keeping filters.

### Two AI systems (Milestone 4, corrected 2026-10-17)

**SYSTEM A — SignalForge Intelligence** (SignalForge's Gemini key; never the customer's Claude):
- `src/lib/ai` (pure): prompts and Zod schemas (taxonomy: relevance relevant/irrelevant/uncertain, sentiment toward the product, 8 categories, signals, severity, area, confidence), pipeline stage gates, `semantic.ts` (embedding grouping + merge candidates), `cluster.ts` (word-based fallback, reconciliation), `priority.ts`, `evaluation.ts` (shadow relevance), `pricing.ts`, `providers.ts` (Gemini via `@google/genai`), `mock.ts` (test classifier).
- `src/lib/server/ai`: `gateway` (availability from server env; reserve → call → settle/release, also for embeddings), `classify` (writes AI columns + history only), `clusters` (embeddings → semantic groups → throttled, cached merge checks → priority → reconcile), `investigate` (spike explanations at product/platform/keyword level with measured facts; issue summaries).
- Pipeline: ingestion is never blocked. The tick queues `ai.classify` every 5 minutes for products with waiting mentions in workspaces where Intelligence can run; "Classify now" queues one immediately. Jobs use the existing queue/leases; retries are idempotent (`processing_status`, attempts, cache by content hash). Realtime `ai` events refresh pages.
- Failure isolation: AI never writes `relevance_status`, the mention allowance or collection/analytics tables.

**SYSTEM B — Developer agent** (the customer's Claude; SignalForge runs no model and pays nothing):
- `src/lib/agent` (pure): OAuth rules (redirects, PKCE, DCR validation, metadata), signed redirect state, task state machine, context package, report schemas, approval scope, routine client, GitHub App client.
- `src/lib/server/agent`: `oauth-store` (hashed codes/tokens, rotation, reuse detection, revocation, membership re-check on every request), `mcp` (MCP server: 7 read tools + 3 agent tools, every query filtered by the token's workspace), `tasks` (readiness, investigation with acknowledgement, approval, single-use implementation, PR verification, timeouts).
- Routes: `/api/mcp` (stateless Streamable HTTP), `/api/oauth/*`, `/.well-known/*`, `/oauth/authorize` (consent), `/api/github/{install,callback}`, dev-only `/api/dev/mock-routine`.
- Workflow: investigation (instructed: no code changes; not technically enforceable) → report → admin approval of the exact plan hash (bound to workspace, issue, repository, environment) → implementation task (approval used once) → PR reported via MCP and checked with the GitHub App.
- **Customer-facing connection (Settings → Claude, 2026-10-18):** one state per card, from `lib/agent/connection-state.ts`: *Not connected*, *Connecting* (access approved in SignalForge but Claude hasn't called yet), *Connected* (an unrevoked grant has been used by a real MCP request — any authenticated request sets `last_used_at`), *Needs attention* (connected, but the routine reports an error), *Unavailable* (production server without a public HTTPS address, which Claude's apps can't reach; development servers stay connectable through Claude Code on the same machine). "Connect Claude" is a three-step dialog: copy SignalForge's address, open Claude's Connectors page (`claude.ai/customize/connectors`, the documented path — Claude documents no link that pre-fills a connector, so SignalForge doesn't fake one), approve on SignalForge's consent page; the page re-checks every few seconds. The MCP URL, the Claude Code command and plan notes are only under "Having trouble connecting?". GitHub repository and the optional routine are separate cards; detailed internal states are under "Manage connection". "Disconnect" revokes every grant of the workspace.

## Data model

Migrations: `supabase/migrations/2026101400000{1..7}_*.sql` (7 = collection: scans, rate-limit buckets, source health, scheduler, ingest) `202610150000{01..03}` (M2.5 platforms; monitoring v2 + cost control; M3 analytics functions) and `202610160000{01..06}` (automatic monitoring: rankings, interval changes, plan search cap, mention pagination index; engagement fix; keyword coverage — SQL first-5 sync retired, `apply_query_groups` disables every unplanned row; retry key includes the failure count so a failed check's quicker retry isn't swallowed by the interval bucket; 05 = Free/Pro/Scale plans, keyword allowance trigger, billing periods, mention usage periods, billable metering, overflow queue, usage RPCs, scheduler priority and allowance pause, paid budget context, keyword conflict columns; 06 = internal plan grants; 07 = Discovery Engine V2: arrival estimates, execution span/continuation columns, V2 activity columns, product history preference, backfill runs/tasks + scheduler, spike confidence + keyword spikes + spike evaluations + `keyword_series`, `workspace_events` + Realtime publication, `svc_enqueue_job`; 08 = coverage: partial wins over complete). All additive (08 replaces one function; no data changes). Later: `202610170000{01..04}` (AI, developer agent, membership-once RLS), `202610180000{01..08}` (competitors, insights, invitations, staff costs, AI spend retention, Stripe, email, security hardening) and `20261019000001` (`keyword_platform_counts`, read-only).

- **Tenancy:** `profiles` (1:1 auth.users) · `workspaces` · `workspace_members(role: owner/admin/member/viewer)`. A deferred constraint trigger guarantees every workspace keeps an owner.
- **Plans & billing:** `plans` (all limits and prices are rows, not code: price, keywords, mentions, floor, keyword refresh target, scheduling priority, `retired_at`) · `subscriptions` (written only by the server from verified webhooks; its `current_period_start/end` anchor billing periods) · `billing_events` (webhook idempotency) · `mention_usage_periods` (per workspace per billing period: plan, allowance, consumed, held, exhaustion time; members can read, nobody but definer functions can write) · `mention_overflow` (held billable mentions; not readable by users) · `usage_counters` (operational). `internal_plan_grants` (staff-only internal testing entitlements: a plan's limits without a subscription; members read, service role writes). `private.effective_plan_id` = active internal grant, else an active subscription, else `free`; `private.billing_period` rolls the stored period forward in whole months keeping its anchor day; `workspace_usage(ws)` returns the current period's usage to members.
- **Products:** `products` · `product_aliases` (kind, ambiguity flag, required context terms, negative terms) · `competitors` · `product_events` (launch markers).
- **Sources:** `integrations` (non-secret config + health) · `credential_secrets` (ciphertext only, no client access) · `ai_provider_connections` (metadata + last-4 hint) · `oauth_states` · `monitoring_queries` (query, cursor, next_run_at).
- **Jobs:** `jobs` (idempotency key, attempts, lease) · `job_runs` (history per attempt) · `job_locks` (named distributed locks) · `coverage_windows` (which time windows each source actually covered) · `api_usage_events`.
- **Monitoring (M2.5):** `product_source_settings` · `launch_boosts` · `monitoring_executions` (per-run log incl. interval decision and reasons, no prices) · `platform_activity` (score, rank, components, trend, coverage, recommended vs actual interval, reasons per product + platform) · `monitoring_interval_changes` · `comment_expansions` · service-only `provider_pricing`, `plan_paid_allowances`, `api_budgets`, `api_cost_ledger`, `api_cost_allocations`, `billing_reconciliations`.
- **Discovery V2:** `arrival_estimates` (per query group posteriors, members read) · `backfill_runs` / `backfill_tasks` (progress, cursors; members read, service writes) · `workspace_events` (realtime signals, kept a day) · `buzz_keyword_spikes` · `spike_evaluations` (latest status per scope: evaluated / insufficient data).
- **Mentions & analysis:** `mentions` (unique on product+source+external_id; content hash; repost link; publication and discovery time; mention type, collection method, data provider, community, link target, estimated-date flag; relevance, sentiment, category with confidences) · `buzz_spikes` · `mention_classifications` (full history incl. manual corrections) · `feedback_clusters` + members · `daily_mention_stats` (UTC-day aggregates that all charts read) · `ai_usage_records` · `ai_investigations` (confirmed / hypotheses / assumptions + evidence) · `notification_preferences` · `notifications` (dedupe key) · `reports` · `audit_logs`.

Cross-tenant linking is structurally impossible: child tables reference `(id, workspace_id)` composite keys, so an alias, mention or cluster cannot point at another workspace's product even via the service role.

## Security model

1. **Authentication:** Supabase Auth. Sessions in httpOnly cookies via `@supabase/ssr`; `proxy.ts` refreshes them. Server code uses `auth.getUser()` (validated with Supabase), never the unverified cookie payload.
2. **Authorization, three layers:** (a) server actions call `requireWorkspaceRole(workspaceId, minRole)` and never trust ids from the client; (b) queries run as the user so Postgres RLS applies; (c) table-level grants are revoked and re-granted per table/column, so e.g. users can update `mentions.sentiment` but not `mentions.content`, and cannot read `jobs.locked_by`.
3. **Plan limits** are enforced by Postgres triggers (serialised with advisory locks), not UI checks. Triggers skip unauthorised writers so plan details aren't leaked to non-members.
4. **Secrets:** AES-256-GCM, key from `CREDENTIALS_ENCRYPTION_KEY`, workspace id bound as AAD, versioned for rotation. Stored in `credential_secrets`, which has no grants for `anon`/`authenticated`. Only the last 4 characters are ever returned.
5. **CSRF:** Server Actions only accept same-origin POSTs; OAuth uses PKCE with the verifier in an httpOnly cookie; `safeRedirectPath` blocks open redirects.
6. **Untrusted input:** website URLs reject private/loopback hosts (prevents SSRF once docs are fetched in M5). From M2, all fetched social content and repository files are treated as data in AI prompts, and AI outputs cannot trigger external actions without explicit user confirmation.
7. **Headers:** HSTS, `X-Frame-Options: DENY`, `nosniff`, strict referrer and permissions policies.
8. **Audit:** triggers record changes to workspaces, memberships, products, integrations and AI connections (never secret columns).

## Job system

- `private.enqueue_job(kind, idempotency_key, …)` — idempotent by key (e.g. `mq:<query_id>:<interval bucket>`, `scan:<scan_id>:<query_id>`).
- `private.defer_job` — postpone without consuming an attempt (rate limits are not failures).
- `private.claim_jobs(worker, limit, lease)` — `FOR UPDATE SKIP LOCKED`; reclaims jobs whose lease expired (worker crash recovery).
- `private.complete_job` / `private.fail_job` — only the lease holder may finish a job; retries use exponential backoff `30s·2^(n-1)` (max 6h) with ±20% jitter, or the source's `Retry-After`; exhausted jobs are dead-lettered.
- `private.try_acquire_lock` — named TTL locks so only one scheduler tick runs at a time.
- Trigger: Supabase Cron calls `/api/jobs/tick` every 2 minutes with `JOBS_TICK_SECRET` (constant-time compare). Each tick enqueues due `monitoring_queries` and works for ~50 s at most. Nothing depends on a browser being open. History: `job_runs` per attempt; recent runs are shown on the Integrations page.
- Server reaches private functions through `public.svc_*` wrappers executable only by `service_role`.

## Analytics (M3)

- **Live SQL, caller's RLS:** `buzz_series` (per bucket × platform: relevant / irrelevant / pending, posts / comments, engagement), `buzz_totals` (per platform, incl. distinct authors, excluded duplicates, undated rows) and `buzz_coverage` (share of each bucket covered by complete / partial windows, merged with `range_agg`) are `SECURITY INVOKER`, so users can only aggregate their own workspace. Day buckets follow the viewer's IANA time zone (cookie set by the browser). `daily_mention_stats` (UTC) is not used: it can't follow time zones.
- **Counting rules:** originals only (exact duplicates and reposts excluded); publication time, not discovery time; rows with no publication date (web results) stay out of time series and are counted separately; late-arriving mentions update past periods.
- **Gaps:** a platform's bucket is *measured* when monitoring covered ≥50% of it (or it has data); otherwise it is `null`. Unmonitored buckets render grey ("not monitored"), never zero. Partially monitored buckets are flagged.
- **Growth:** `(cur − prev) / prev`; prev = 0 ⇒ "New activity"; previous period essentially unmonitored ⇒ "No earlier data to compare"; either period < 90% completely monitored ⇒ flagged "incomplete data".
- **Virality (experimental, 0–100):** mention growth vs the product's own 28-day baseline (35%), distinct-author growth (20%), engagement per mention (15%), platform spread (15%), acceleration vs the previous day (15%); ratios on a log scale with pseudo-counts, then damped by volume (n/(n+5)) so 1 → 3 isn't viral and size alone never scores. Uses only platforms completely monitored over the baseline. Not sentiment.
- **Mentions and spikes graph (2026-10-18):** Buzz shows one time-axis graph for one scope at a time — all activity (`buzz_series`), a platform (same, filtered) or a keyword (`keyword_series`) — over the global range. Spikes for that scope are markers (confirmed: filled triangle; possible: hollow circle); unmonitored periods are shaded and the line breaks there; partly monitored periods are shaded lighter. A marker opens a side panel: observed vs expected, contributing platforms (`buzz_totals`) and keywords (`keyword_platform_counts`) and the most engaged relevant mentions for that period (`spikeDetailsAction`, caller's RLS), plus the existing spike explanation (Gemini, on request only, cited).
- **Spikes (V2, `spikes-v2.ts`):** for product, platform and keyword series (publication time), each period is compared with its own baseline of completely monitored periods (28 days / 7 days of hours; winsorized at the 90th percentile; seasonal weekday/hour factor once 3 cycles exist): upper-tail probability under a negative binomial (Gamma–Poisson predictive, variance ≥ MAD² and sample variance), plus effect size (ratio ≥ 1.5, robust z). **Confirmed** = p < 10⁻⁴, z ≥ 3, complete period, ≥ 7 days / 48 h of baseline; **possible** = unusual (p < 10⁻²) on a partly monitored period or a short baseline, or strong evidence against a baseline of partly monitored (lower-bound, non-zero) periods; **insufficient data** = < 3 days / 12 h of complete baseline (stored in `spike_evaluations`). No universal mention threshold. The product series is complete only when every non-ranked platform read the period completely (a cut-off search makes it a lower bound). The hourly job re-judges the whole evaluated range (up to 400 days of history) so backfilled periods are evaluated too, replacing stale rows, for products with new mentions or backfill progress in 2 h and any monitored product not evaluated in a day; errors are logged, not swallowed.
## Competitors

A competitor is a `competitors` row plus a hidden **tracking product** (`products.competitor_of` → the product). Everything keyed on `product_id` — query planning, collection, dedup, classification, spikes, `buzz_*` functions — therefore works for competitors without a `competitor_id` filter anywhere, and a post mentioning both a product and its competitor is stored once for each. Tracking products are filtered out of product lists (`competitor_of is null`) and product/keyword limits; writes go through `add_competitor`/`update_competitor`/`remove_competitor`. Comparisons (`src/lib/analytics/competitors.ts`) use only sources monitored for every compared product and only the period all were tracked.

## Mentions list

- **Numbered, server-side pagination** (`?page=N`, 20 per page): offset over a deterministic order `(published_at desc, id desc)` served by `mentions_product_published_id_idx`, with an exact count for page numbers and "Showing 21–40 of 292". Offsets were chosen over the earlier keyset cursor because page numbers need random access; the order's unique tie-breaker keeps pages disjoint and gap-free on a stable dataset (rows inserted while someone pages can shift later pages by a row — the same trade-off any numbered list makes). A page past the end redirects to the last page.
- **Filters in the URL:** platform, type, relevance, text search, duplicates and the global date range. Every page link keeps them; changing a filter returns to page 1 and pushes a history entry, so Back/Forward work. The old `cursor` parameter is ignored.
- **Cards:** platform, type, community, author, time (estimated dates labelled), relevance status (rule-based "Keyword match" vs "Needs review" vs the team's own Relevant / Not relevant), title, a 4-line preview with Read more (the full stored text is in the page, `dir="auto"` + `lang`, never translated), matched keywords, engagement, "Open original / Open thread" (what the link really opens), and Relevant / Not relevant toggles that store the team's decision (`aria-pressed`, undoable).
